# Jev (TypeSafe System One) — как с ним работать

Проверено на живом API 2026-09-21. Ключ `TYPESAFE_API_KEY` в `~/.dsh/.credentials.yaml`.
Официальные документы: https://docs.typesafe.ai/ — эндпоинт `POST /v1/systemone`.

---

## Главный вывод

**Jev не считает — он судит.** Первый прогон калибровки провалился не из-за языка и не
из-за модели: я просил её самой вычислить сумму статов и сравнить с нормой. Результат —
все 20 карт получили 2.09–2.15 при уверенности 0.64, то есть середина шкалы.

Когда арифметику посчитал код, а модели осталось только суждение — **20/20 и три
прогона без единого расхождения**.

Это не случайность и не особенность Jev: это его штатный режим. TypeSafe называет
принцип «keep code in control» — код владеет логикой, модель выносит узкое суждение.
Нарушение принципа выглядит как «модель сломана», хотя сломана рубрика.

## Четыре правила, выведенные из проб

| Правило | Доказательство |
|---|---|
| **Числа считает код.** Модели отдаём готовые значения | с сырыми данными 13/20, с посчитанными — 20/20 |
| **Состояние — простой строкой**, не JSON-объектом | объект: 0.73 / 0.89; та же мысль строкой: 0.97 / 0.97 |
| **Noul вместо Score** для оценок | Score по шкале 5 или 3 уровней: разброс 0.06–0.09 (середина шкалы); Noul: разделение классов 0.95 |
| **Решение принимает код** по вероятности | порог 0.5 в коде, а не «мнение модели» |

## Что работает идеально (проверено)

| Примитив | Проверка | Результат |
|---|---|---|
| Noul | «Кот спит?» / «Кот летит?» — английский | 0.98 / 0.01 |
| Noul | то же по-русски | 0.97 / 0.01 |
| Choice | что лежит на столе: помидор / машина / планета | `tomato`, уверенность 1.00 |
| Score | 2 конкретных уровня: зрелый / незрелый помидор | 1 / 0, уверенность 1.00 |
| Noul | суждение о балансе карты по готовым числам | 20/20, вероятности 0.98 против 0.03 |

**Русский язык работает не хуже английского** (разница 0.01–0.05). Риск, которого я
боялся в ТЗ, не подтвердился.

## Первый рабочий результат: аудит баланса карт

`npm run jev:balance` — прогон направления Б. Арифметику считает код (2 стата за ману
минус цена ключевых слов плюс отставание от карт той же цены), модель отвечает на один
вопрос: оправдывает ли нехватку текст способности.

**Итог по 39 существам:** 34 в норме по коду, 5 требовали суждения, **находок ноль** —
все пять оправданы способностями.

| Карта | Мана | Статы | Нехватка | Чем оправдана | p |
|---|---|---|---|---|---|
| Мэр Омска | 8 | 4/7 | −4.5 | усиление всего стола, 2 токена | 0.80 |
| Чёрная Дыра | 7 | 5/5 | −4.0 | массовое уничтожение | 0.60 |
| Дракон Иртыша | 9 | 7/7 | −2.5 | 3 урона всем врагам | 0.67 |
| Писинер Школы 21 | 3 | 1/3 | −2.0 | разгон маны и добор | 0.68 |
| Лорд Кластера | 7 | 5/7 | −2.0 | усиление стола, заморозка | 0.77 |

**Это не «проблем не найдено», а проверенный факт:** дорогие карты систематически
недобирают статы (7–9 маны: −2…−5), и у всех пяти такая недобранность оплачена
способностью. Дизайн кривой дорогих карт согласован.

**Кандидат на взгляд человеком — Чёрная Дыра** (p=0.60, самая низкая): уничтожение
условное, только существ с атакой ≤2, и в мете больших существ карта может не окупаться.

### Контроль прибора — обязателен

`npm run jev:balance-control` — те же карты, те же числа, но текст способности **затёрт**.

| | Средняя вероятность «нехватка оправдана» |
|---|---|
| настоящие тексты | **0.728** |
| тексты затёрты | **0.046** |

Сдвиг 0.68, и ни одна карта без способностей не признана оправданной. Узкий диапазон
0.60–0.80 в аудите означает не сжатие шкалы, а то, что все пять карт действительно
мощные. **Без этого контроля отчёту верить нельзя** — вероятности 0.70–0.78 одинаково
похожи и на различение, и на ответ «да» по умолчанию.

## Файлы

| Файл | Назначение |
|---|---|
| `extract-cards.mjs` | выгрузка карт из `src/data/cards.ts` в `reports/cards.json` (парсером TypeScript) |
| `judge-stability.mjs` | **ворота**: точность и устойчивость правильной формы, 3 прогона |
| `fact-vs-judgment.mjs` | доказательство главного вывода: сырые данные против посчитанных |
| `probe-primitives.mjs` | проверка примитивов на заведомо известных ответах |
| `discriminate.mjs` | проверка прибора на заведомо различимых входах |
| `probe-classify.mjs` | проба разметки способностей (выявила правило «одна ось на вопрос») |
| `balance-audit.mjs` | **направление Б**: отчёт по балансу, `npm run jev:balance` |
| `balance-control.mjs` | контроль прибора к аудиту, `npm run jev:balance-control` |

Тупиковые прогоны удалены, их выводы зафиксированы выше: `calibrate.mjs` (абстрактный
Score по 5 уровням), `rubric-vs-fact.mjs` (Score по 3 уровням) — оба воспроизводили
ошибку «середина шкалы» и больше не нужны.

## Если берёшься за новую задачу

**Переносимая версия всего этого опыта живёт скиллом `jev-decision-judge`**
(`~/.dsh/skills/jev-decision-judge/`) — он виден в любом чате и любой задаче, а не только
в этом проекте. Там же клиент `scripts/jev.mjs` с журналом опыта и синтез выводов в
`references/jev-insights.md`. Перед новой задачей для Jev лучше начать оттуда.

1. Сформулируй, **какие числа считает код** — если модель должна считать сама, задача
   поставлена неверно.
2. Составь **Noul-вопрос**, а не «оцени по шкале».
3. Прогони на 20 примерах, где ответ **известен заранее** — иначе не отличишь
   понимание от угадывания среднего.
4. Проверь **устойчивость**: тот же набор в другом порядке должен дать те же вердикты.
5. Запиши исход в журнал скилла — иначе опыт не накопится.
